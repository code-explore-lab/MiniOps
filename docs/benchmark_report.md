# MatMul Benchmark 报告（M3：朴素基线）

本报告记录 `miniops::matmul` 朴素 ijk 实现的单线程基线数据。后续优化版本
都必须与这里的数据做对比，因此先固定测试方法、环境和口径。

## 1. 测试环境

| 项目 | 内容 |
| --- | --- |
| 机器 | AMD Ryzen 7 5800H（8 核 16 线程，标称基频 3.2 GHz） |
| 内存 | 16 GB（15.35 GiB 可用） |
| 操作系统 | Windows 11 Home China，版本 10.0.26300 |
| 编译器 | TDM-GCC 10.3.0（`C:/TDM-GCC-64/bin/c++.exe`） |
| CMake / 生成器 | CMake 4.4.3 / Ninja 1.13.2 |
| 构建类型 | `Release` |
| 编译选项 | `-O3 -DNDEBUG -std=c++17 -Wall -Wextra -Wpedantic` |
| 算子版本 | `naive`，朴素 ijk，单线程 |
| 数据布局 | row-major，`float` 连续内存 |

## 2. 测试方法

- **Release 构建**：Debug 构建会关闭优化，计时没有参考价值；程序在未定义
  `NDEBUG` 时会打印警告。
- **预分配内存**：每种规模的 `A`、`B`、`C` 只在计时前分配一次，计时区间内
  不进行任何内存分配。
- **预热**：每种规模先执行 2 次不计时的 `matmul`。
- **重复次数**：默认自动选择。先试跑一次，以约 500 ms 采样总时长为目标，
  小矩阵多测、大矩阵少测，限制在 7～2001 次之间。实际操作中：
  64² 重复 1581 次，128² 重复 176 次，256² 重复 24 次，512²/1024² 各 7 次。
- **统计量**：**中位数（median）**。同时记录均值、最小值、标准差用于判断
  波动。
- **防优化**：计时后对输出矩阵求 checksum 并检查 NaN/Inf。所有规模两次独立
  运行的 checksum 完全一致，说明结果稳定。
- **计时区间**：只包含 `miniops::matmul(...)` 调用本身，不包含数据填充、
  checksum 计算和内存分配。

GFLOP/s 按 `2 * M * N * K / (t × 1e9)` 计算，其中 `t` 为秒；加速比按
`T_baseline / T_optimized` 计算。

当前所有行都是基线自身，所以加速比均为 1.00×。后续加入优化的实现后，应在
同一台机器、同一次测量会话中增加对应的行，再计算加速比。

### 3.1 GFLOP/s 观察

- 64² 的工作集很小，基本驻留在缓存中，单线程吞吐约 3.2 GFLOP/s。
- 128²～256² 时工作集超过单核 L2，吞吐降到约 1.6 GFLOP/s。
- 512² 起 `B` 的列访问跨步明显增大，缓存命中率下降，吞吐约 0.7 GFLOP/s。
- 1024² 时每个矩阵约 4 MB，吞吐进一步降到约 0.38 GFLOP/s。

作为参考，Ryzen 7 5800H 单核 AVX2/FMA 的 FP32 理论峰值约为
`16 FLOP/cycle × 3.2 GHz ≈ 51 GFLOP/s`（仅为粗略上限）。朴素实现没有显式
向量化和缓存分块，距离该上限还有很大空间，这也是后续优化的主要方向。

## 4. 可复现性说明

不同测量会话之间存在明显波动，尤其是 512² 和 1024²。本次开发过程中观察到：

| 规模 | 不同会话的中位耗时范围 (ms) |
| --- | ---: |
| 64 | 0.155 ～ 0.179 |
| 128 | 2.579 ～ 3.301 |
| 256 | 20.720 ～ 25.056 |
| 512 | 253.506 ～ 364.886 |
| 1024 | 4119.796 ～ 5687.325 |

这是笔记本 CPU 的睿频/温度/功耗策略以及后台进程共同造成的，不是算子实现
变化。结论：

1. 报告中的加速比必须来自**同一会话、同一机器状态**下的前后对比，不能拿
   不同日期跑出的两个绝对值直接相除。
2. 大矩阵对持续负载更敏感，比较优化版本时建议把不同版本交替测量、重复多轮，
   并同时报告中位数和波动范围。
3. 计时前尽量关闭浏览器、IDE 索引等占用 CPU/内存带宽的任务。

## 5. 复现命令

```bash
# 配置 Release 构建（Windows + Ninja）
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release

# 构建
cmake --build build-release

# 运行基线并保存 CSV（自动选择重复次数）
./build-release/benchmark_matmul.exe --csv docs/benchmark_matmul_naive.csv

# 也可以固定重复次数、指定规模
./build-release/benchmark_matmul.exe --repeats 7 --warmup 2 --sizes 128,512
```

## 6. 结论

- 朴素单线程 MatMul 的基线已经建立，数据可重复、checksum 一致。
- 性能随规模下降明显：64² 约 3.2 GFLOP/s，1024² 仅约 0.38 GFLOP/s，主要
  瓶颈是缓存未命中和 `B` 的非连续访问。
- 下一步优化（循环重排、分块、SIMD、OpenMP）必须使用同一套 benchmark 和
  同一会话内的对比方式验证收益。
