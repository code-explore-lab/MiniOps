# MatMul Benchmark 报告（M3：基线、内层循环优化与 OpenMP）

本报告记录 `miniops` 中各 MatMul 实现的性能，重点回答四个问题：

1. 内层循环是否重复读取相同数据？
2. 是否反复写回输出？
3. 是否发生不必要的数据复制？
4. 热路径中是否动态分配内存？

针对每个问题实现了独立变体，并分别 benchmark。所有加速比以同规模的
`naive` 实现为基线，且来自同一次运行内的交替测量。第 4.4 节另外记录
OpenMP 多线程的线程扩展；那部分使用独立的 clang 构建，只在同一次运行内
比较，不与 GCC 的绝对耗时混用。

## 2. 问题与对应改动

| 观察到的问题 | 对应实现 | 改动 |
| --- | --- | --- |
| `ijk` 内层沿 `p` 读 `b[p*n+j]`，跨步访问 | `ikj` | 循环重排为 `i-k-j`，内层 `j` 连续访问 `B`、`C` |
| `a[i*k+p]` 在内层反复参与计算 | `ikj` | 提前装入 `const float a_ip` 局部变量 |
| 分块内反复计算 `(ii+i)*n + (jj+j)` 并跨步访问 | `blocking_ptr` | 提前算好 `a_row`、`c_row`、`b_row` 指针，内层 `j` 连续 |
| 同一行 `B` 被每个输出行重复读取 | `rows2/rows4/rows8` | 一次处理多个输出行，让 `B` 行在 L1 中被复用 |
| 每个 `p` 都读改写 `C` 一次 | `reg4/reg8/reg16` | 输出块留在寄存器中累加，最后只写回 `C` 一次 |
| 单核性能受限于一个核心 | `omp/omp_ikj` | 按输出行划分给多个线程；每个输出元素仍由单线程累加 |
| 热路径动态分配 / 数据复制 | 所有实现 | 无堆分配；只使用调用方内存和栈上小块，未复制 `A/B/C` |

## 3. 测试方法

- **Release 构建**，程序在未定义 `NDEBUG` 时打印警告。
- **预分配**：每种规模的 `A`、`B` 和每个实现的 `C` 只在计时前分配一次。
- **预热**：每个实现先执行 2 次不计时的 `matmul`。
- **重复次数**：自动选择。对每个实现试跑一次，以最慢实现约 500 ms 采样
  总时长为目标，限制在 7～2001 次；同一规模下所有实现使用相同重复次数。
- **交替测量**：每轮轮转实现顺序，避免某个实现总是处于固定缓存/温度状态。
- **统计量**：中位数（median），同时记录均值、最小值、标准差。
- **正确性**：计时后对每个输出求 checksum 并检查 NaN/Inf；所有实现结果
  逐位一致，跨运行稳定。
- **筛选与聚焦**：`--impls` 可只运行指定实现，用于降低多实现交替带来的
  缓存/温度干扰。每项改动先用筛选跑，再对领先实现做聚焦复测。
- **线程扩展**：`--threads` 指定 omp 实现的线程数。多个线程数之间也轮转
  测量，并与串行实现放在同一次运行中；线程数 1 的结果包含在串行组里。

GFLOP/s 按 `2 * M * N * K / (t × 1e9)` 计算；加速比为 `T_naive / T_impl`。

16 线程时 `omp_ikj` 在 1024² 的中位耗时本次会话为 27.9 ms（约 77.1 GFLOP/s），
相对串行 `ikj` 为 6.28 倍；另一次聚焦复测为 32.0 ms（约 67.1 GFLOP/s）、
4.57 倍。绝对值和相对加速比都随整机频率/温度漂移，但方向稳定。相同线程
数下 `omp_ikj` 全面快于 `omp(reg8)`：单线程快 1.4～3.4 倍，16 线程快
1.3～2.6 倍（覆盖两次会话）。

线程收益在 8 线程（8 个物理核）时已接近饱和；16 线程（SMT）只再带来
1.1～1.4 倍提升：1024² 从 39.2 ms 降到 27.9 ms（复测 42.7→32.0 ms），
512² 从 4.70 ms 降到 3.82 ms（复测 4.61→4.09 ms），256² 从 0.544 ms 降到
0.485 ms，128² 基本持平。128² 单次计算不到 0.1 ms，线程同步和调度开销
占比高，8 线程之后不再提升。

本机的 clang/MSVC 工具链不提供 ThreadSanitizer，因此没有做 TSan 运行。
数据竞争由行划分本身消除：每个线程只写 `C` 中互不相交的行；测试和
benchmark 还额外校验了 1～16 线程的 checksum 与单线程一致。

## 5. 分析

### 5.1 为什么 `ikj` 收益最大

`naive` 的最内层沿 `p` 递增，`b[p*n+j]` 每次跨 `n` 个 float，几乎每次访问
都落在不同缓存行；`ikj` 固定 `p` 后沿 `j` 连续读取 `B` 行、连续读改写 `C`
行，缓存行利用率高，且编译器的内层 `j` 循环可以自动向量化（SSE 16 字节）。
实测 `ikj` 在 128² 达到约 22.6 GFLOP/s，1024² 仍有约 14.3 GFLOP/s。

### 5.2 为什么 `reg*` 输出块累加反而更慢

`reg4/reg8/reg16` 把 `C` 的若干列放进寄存器，理论上减少了 `C` 的重复读写。
但 GCC 10 在 `-O3` 且没有 `-ffast-math` 时，不能对浮点累加做重结合，
内层 `acc[t] += av * b_row[t]` 没有像 `ikj` 的 `j` 循环那样被向量化；
实际生成的是标量 FMA/加法，于是性能下降到 `ikj` 的 1/2～1/3。

这说明在当前编译器和选项下：**`C` 的反复写回不是瓶颈，失去向量化才是**。
寄存器分块要在标量代码里发挥威力，需要显式 SIMD intrinsic，或允许
`-ffast-math`（会改变浮点语义，不推荐直接用于正确性测试）。

### 5.3 为什么行复用只有 1024² 有收益

`rows4` 让一行 `B` 在一个 `i` 块内被 4 个输出行复用，减少 `B` 从 L3/内存
的重复读取。128²～512² 的 `B` 工作集还比较小，命中缓存后瓶颈在计算而不是
内存，因此收益在噪声内；1024² 时 `B` 为 4 MB，缓存压力明显，行复用才体现
出约 2%～12% 的提升。两次聚焦测量方向一致，但幅度受整机状态影响较大。

### 5.4 分块与指针提升

`blocking` 的 `BM=32, BN=32, BK=16` 在当前缓存层级下收益为负；它增加了三层
循环和块边界判断，却没有寄存器分块/SIMD。`blocking_ptr` 只是把下标算术
提前，获得 2%～5% 的小幅改善，仍无法弥补分块本身的开销。

### 5.5 动态分配与数据复制

三个层面的代码都没有在热路径分配内存：输入输出由调用方提供，行复用只使用
栈上的指针数组，寄存器分块只使用栈上固定长度数组。也没有复制 `A/B/C`。
因此这一项不需要额外改动。

### 5.6 为什么 `omp_ikj` 快于 `omp(reg8)`

两个 OpenMP 实现的行划分和写集合完全相同，差别只在每个线程调用的内核：

- `omp_ikj` 每行先清零 `c_row`，再执行 `ikj` 的 `p-j` 循环。`j` 循环连续
  访问 `B`、`C`，clang 能向量化（宽度 4，双路展开）。
- `omp` 每行调用 `matmul_row_regblock<8>`。正如 5.2 所示，这种寄存器累加
  写法没有获得同样的向量化：1024² 单线程比 `ikj` 慢约 2.7 倍，其他规模也
  普遍更慢。增加线程只能把这个固定劣势按比例摊薄，无法消除。

一个容易踩的坑：直接把 `ikj` 内核放进 `#pragma omp parallel for` 后，
clang 报 `Cannot vectorize uncountable loop`，内层 `j` 循环完全不再向量化，
单线程反而比串行 `ikj` 慢约 4 倍。原因是 OpenMP outlining 之后 `n` 的
范围信息丢失，编译器无法证明循环可计数。在循环体内加 `const int nn = n;`
局部副本即可恢复向量化。

线程扩展的上限主要来自内存带宽和 SMT。8 个物理核已经提供相对串行 `ikj`
3.3～6.0 倍的加速；16 个逻辑线程只再增加 1.1～1.4 倍。128² 基本持平，
256² 只有 1.12 倍，1024² 最高 1.41 倍。

另外，`omp_ikj` 的单线程结果比串行 `ikj` 还快约 1.1～1.4 倍。两者内层
循环相同，差别是 `ikj` 先整体清零 `C` 再累加，而 `omp_ikj` 在每行开始时
就地清零，省掉了一次对 `C` 的完整遍历，局部性也更好。这是实现细节带来
的额外收益，不是线程带来的。

## 6. 可复现性说明

不同测量会话之间存在明显波动，1024² 尤其明显。开发过程中 `naive` 的
中位耗时范围：

| 规模 | 不同会话的中位耗时范围 (ms) |
| --- | ---: |
| 64 | 0.126 ～ 0.185 |
| 128 | 2.427 ～ 3.301 |
| 256 | 20.720 ～ 26.738 |
| 512 | 253.506 ～ 434.880 |
| 1024 | 4119.796 ～ 7027.155 |

因此：

1. 加速比必须在同一次运行内、交替测量得到，不能跨会话拿绝对值相除。
2. 先用全部实现筛选趋势，再对领先实现做聚焦复测；两次结果方向一致才下结论。
3. 计时前尽量关闭浏览器、IDE 索引等占用 CPU/内存带宽的任务。

OpenMP 部分在 16 线程时波动更大（Windows 调度、SMT 频率和内存带宽竞争），
同一配置在不同会话之间可差 20%～30%。因此 4.4 节只使用同一次运行内的
中位数和加速比，不跨会话比较绝对耗时。

## 8. 结论

- 内层连续访问（`ikj`）是决定性的优化，5.3×～42.3×，应作为后续优化的基准。
- 输出块寄存器累加（`reg*`）在当前 GCC 10 标量代码下是负优化，根因是浮点
  累加无法自动向量化；这项要等到显式 SIMD 阶段再重做。
- 行复用（`rows4`）只在 1024² 有小幅收益，且不稳定；暂不引入，避免代码
  复杂度上升。
- 分块（`blocking`）当前配置不如 `ikj`，指针提升只能带来个位数百分比改善。
- OpenMP 有效且可扩展：`omp_ikj` 在 16 线程、1024² 上为 27.9～32.0 ms
  （约 67～77 GFLOP/s），是同规模串行 `ikj` 的 4.6～6.3 倍（两次会话）。
  8 个物理核时已接近饱和，16 线程（SMT）只再提升 1.1～1.4 倍。
- 并行实现的内核选择比线程数更重要：相同 16 线程下，`ikj` 内核比 `reg8`
  内核快 1.3～2.6 倍。并行化不能修复一个本身较慢的串行内核。
- 下一阶段真正值得投入的方向：显式 SIMD（AVX2/FMA，需要 `-march` 或
  intrinsic）、把向量化微内核与 `omp_ikj` 的行划分结合，以及针对 1024²
  的缓存分块；每一项继续沿用本报告的同会话交替测量方法。
