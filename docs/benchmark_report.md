# MatMul Benchmark 报告（M3：基线 + 优化版本对比）

本报告记录 `miniops` 中三个 MatMul 实现的单线程性能：朴素 `ijk` 基线、
`ikj` 循环重排、以及分块（blocking）版本。三个实现使用同一套计时程序、
在同一次测量会话中交替运行，加速比均以同规模的 `naive` 为基线。

## 1. 测试环境

| 项目 | 内容 |
| --- | --- |
| 机器 | AMD Ryzen 7 5800H（8 核 16 线程，标称基频 3.2 GHz） |
| 内存 | 16 GB（15.35 GiB 可用） |
| 操作系统 | Windows 11 Home China，版本 10.0.26300 |
| 编译器 | TDM-GCC 10.3.0（`C:/TDM-GCC-64/bin/c++.exe`） |
| CMake / 生成器 | CMake 4.4.3 / Ninja 1.13.2 |
| 构建类型 | `Release` |
| 编译选项 | `-O3 -DNDEBUG -std=c++17 -Wall -Wextra -Wpedantic` |
| 线程 | 单线程，未启用 OpenMP/SIMD intrinsic |
| 数据布局 | row-major，`float` 连续内存 |

被测实现：

| 版本 | 说明 |
| --- | --- |
| `naive` | 朴素 `ijk`，`B` 按列跨步访问，基线 |
| `ikj` | 循环重排为 `i-k-j`，`B` 的最内层 `j` 连续访问 |
| `blocking` | 在 `ikj` 基础上按 `BM=32, BN=32, BK=16` 分块 |

## 2. 测试方法

- **Release 构建**：Debug 构建会关闭优化，计时没有参考价值；程序在未定义
  `NDEBUG` 时会打印警告。
- **预分配内存**：每种规模的 `A`、`B` 以及每个实现的输出 `C` 只在计时前
  分配一次，计时区间内不进行任何内存分配。
- **预热**：每种规模先对每个实现各执行 2 次不计时的 `matmul`。
- **重复次数**：默认自动选择。先对每个实现试跑一次，以最慢实现约 500 ms
  的采样总时长为目标，限制在 7～2001 次之间；同一规模下三个实现使用相同的
  重复次数。
- **交替测量**：每个重复轮次内依次运行三个实现，且每轮轮转顺序，避免某个
  实现总是处于固定的缓存/温度状态。
- **统计量**：**中位数（median）**。同时记录均值、最小值、标准差。
- **正确性校验**：计时后对每个输出求 checksum 并检查 NaN/Inf。三个实现的
  checksum 完全一致，且跨运行稳定。原因是三者对每个输出元素都按
  `p = 0..k-1` 的顺序累加，浮点运算顺序相同，结果逐位一致。
- **计时区间**：只包含一次 `matmul` 调用本身，不包含数据填充、checksum 和
  内存分配。

GFLOP/s 按 `2 * M * N * K / (t × 1e9)` 计算，其中 `t` 为秒；加速比按
`T_naive / T_impl` 计算。

## 4. 结果分析

### 4.1 循环重排（ikj）收益最大

朴素 `ijk` 的最内层循环沿 `p` 递增，读取 `b[p*n + j]` 时跨步为 `n`，每次
访问几乎都会落到不同的缓存行；`ikj` 把最内层换成 `j`，固定 `p` 后连续读取
`b[p*n + j]` 和写入 `c[i*n + j]`，缓存行利用率大幅提高，同时便于编译器自动
向量化。

效果：

- 64²：3.75 → 20.09 GFLOP/s（5.35×）
- 256²：1.37 → 24.31 GFLOP/s（17.79×）
- 1024²：0.34 → 15.27 GFLOP/s（44.79×）

规模越大，缓存问题越突出，因此加速比随规模增大。`ikj` 在 128²～512² 保持
约 20～24 GFLOP/s，1024² 时工作集超过 L3 可用容量，降到约 15 GFLOP/s。

### 4.2 当前分块配置没有超过 ikj

`blocking` 在所有规模上都比 `ikj` 慢约 1.3～1.4 倍：

| 规模 | ikj (ms) | blocking (ms) |
| ---: | ---: | ---: |
| 64 | 0.026 | 0.034 |
| 128 | 0.188 | 0.256 |
| 256 | 1.380 | 1.952 |
| 512 | 13.187 | 18.245 |
| 1024 | 140.657 | 193.255 |

可能原因：

1. `BM=32, BN=32, BK=16` 的分块对当前缓存层级并不合适。`ikj` 已经让 `B`
   和 `C` 连续访问，分块额外引入了三层循环和块边界判断开销。
2. 内层仍然是 `i-p-j` 的标量循环，没有做寄存器分块（register tiling），
   每个 `(i,j)` 仍反复读写 `C` 和 `B`，分块带来的缓存收益没有转化为
   FMA 吞吐。
3. 分块只改善了缓存局部性，没有减少指令数；`ikj` 的自动向量化已经足够好。
   若要超过 `ikj`，通常还需要打包（packing）+ SIMD + 多线程。

当前单核 AVX2/FMA 的 FP32 理论峰值约为 `16 FLOP/cycle × 3.2 GHz ≈
51 GFLOP/s`（粗略上限）。`ikj` 最好约 24 GFLOP/s，约为该上限的 47%，说明
仍有优化空间。

## 5. 可复现性说明

不同测量会话之间存在明显波动，尤其是 512² 和 1024²。开发过程中观察到的
`naive` 中位耗时范围：

| 规模 | 不同会话的中位耗时范围 (ms) |
| --- | ---: |
| 64 | 0.126 ～ 0.179 |
| 128 | 2.429 ～ 3.301 |
| 256 | 20.720 ～ 25.056 |
| 512 | 253.506 ～ 417.966 |
| 1024 | 4119.796 ～ 6300.485 |

这是笔记本 CPU 的睿频/温度/功耗策略以及后台进程共同造成的，不是实现变化。
因此：

1. 本报告中的加速比全部来自**同一次运行内**的交替测量，避免跨会话比较。
2. 比较不同优化版本时继续使用同一会话、交替测量的方式。
3. 计时前尽量关闭浏览器、IDE 索引等占用 CPU/内存带宽的任务。

## 6. 复现命令

```bash

# 构建
cmake --build build-release

# 运行全部实现并保存 CSV（自动选择重复次数）
./build-release/benchmark_matmul.exe --csv docs/benchmark_matmul.csv

./build-release/benchmark_matmul.exe --repeats 7 --warmup 2 --sizes 128,512
```


## 7. 结论

- `ikj` 是目前最好的实现：相对朴素基线加速 5.35×～44.79×，
  256² 达到 24.3 GFLOP/s。
- 当前 `BM=32, BN=32, BK=16` 的分块版本正确，但比 `ikj` 慢约 30%～40%，
  不适合作为下一步基线；若继续做分块，应同时调整块大小并引入寄存器分块
  或打包。
- 下一阶段的优化重点建议是：SIMD（AVX2/FMA）、寄存器分块、OpenMP 多线程，
  每项改动都用本 benchmark 的同会话交替测量验证收益。
